# TerraView24

**Damage done by humans, measured against the norm.**

A 3D globe that surfaces human caused environmental events, detected
statistically from satellite data, then corroborated and confirmed against
independent sources before any narrative claim is made.

> **Status: Phase 0.** The architecture is being proved end to end, including the
> trigger layer, before any detection work begins. There is no globe yet and no
> anomaly scoring yet. The deployed page currently reports only its own state.
> That is deliberate: see [docs/ROADMAP.md](docs/ROADMAP.md).

---

## The idea

A fire on a map is not a finding. "There is more burning here than there should
be at this time of year" is a finding, and it is a statement only a model can
make.

So every pin is a **clustered event scored against a multi year seasonal
baseline**, never a raw detection. Events move through four stages, and the
claim the interface makes grows only as the evidence does:

| Stage | Gate | What it claims |
|---|---|---|
| `SUSPECTED` | At least 3 sigma above the regional seasonal norm, or passes absolute floors where no baseline can score it | Nothing. The statistic only |
| `CORROBORATED` | A genuinely independent second signal agrees | "Something real is here" |
| `CONFIRMED` | Scoped news matching finds coverage in the window | A typed event with narrative |
| `UNREPORTED` | Corroborated, aged past the confirmation window, no coverage found, and the news index actually covered that window | **"Satellites saw this. Media did not."** |

`UNREPORTED` is the point of the project. A live map of environmental damage that
was detected but never reported is a finding, not a rendering of someone else's
feed.

**News never places a pin.** Media coverage volume measures media attention, not
event frequency: a fire in Greece gets hundreds of articles and an equivalent
fire in Siberia gets a handful. Plotting coverage would plot Western media
attention. That asymmetry is not a flaw to hide, it is the mechanism that makes
`UNREPORTED` meaningful.

### What a pin says, and what it does not

A confirmed pin reads:

> VIIRS detected sustained anomalous thermal activity, 4.2 sigma above the
> regional October norm, corroborated across three passes by an independent
> sensor. Matching coverage found.

It does **not** read "forest destruction here". The `headline_claim` string is
generated by the pipeline, not the frontend, so the interface cannot overstate
what the data supports. That restraint is the project's credibility.

The same discipline applies to the page's claims about itself. It states how old
its data is, it says plainly when that data is older than it should be, and the
words "real time" do not appear anywhere until an end to end latency has
actually been measured.

## Architecture

Three decoupled tiers connected only by static JSON files, plus one small timer.

```
TIER 0   Offline baseline, run by hand, committed
         Multi year archives  ->  per cell seasonal norms

TRIGGER  Cloudflare Worker, one cron, calls workflow_dispatch

TIER 1   Pipeline, GitHub Actions
         ingest -> cluster -> score vs baseline -> classify
               -> promote stage -> confirm vs news -> emit JSON
         Writes to the orphan `data` branch. Never touches `main`.

TIER 2   Static frontend, Vercel
         Vite, React, CesiumJS, GSAP. Fetches JSON at runtime.
         Zero secrets in the bundle.
```

### Cost and honesty about it

Budget is zero, and every data source has a free tier. But the honest claim is
**no application server and no database**, not "zero servers".

There is **one credential and one always on component**: a free Cloudflare
Worker, and one GitHub fine grained token scoped to Actions write on this
repository alone, expiring every 90 days.

That component exists because GitHub's own scheduler was measured rather than
assumed. Against a control repository over 68.5 days, `schedule` delivered 99.3
percent of windows but with a **4.68 hour median delay**. Against this project,
high frequency crons delivered **3.9 to 5.3 percent** of their windows. The delay
is in run creation, so nothing inside a repository can shorten it. An external
timer calling `workflow_dispatch` was measured at 2.4 to 3.8 seconds.

`schedule` is still present in every workflow as a fallback, because a late run
beats no run. If you would rather not run the Worker at all, that is a supported
choice: delete it and the page automatically states GitHub's slower cadence
instead. See [infra/trigger-worker/README.md](infra/trigger-worker/README.md).

## Development

```bash
# Python pipeline
pip install -r requirements.txt
python -m pytest tests/
python -m ruff check pipeline/ scripts/ tests/

# Workflow linting. A YAML parser is NOT a validator: a file that parsed
# cleanly was rejected by GitHub Actions on every push, reporting only
# "workflow file issue". actionlint catches that exact case.
bash scripts/get-actionlint.sh
./tools/actionlint .github/workflows/*.yml

# Ground rule: no en or em dashes anywhere
python scripts/check_no_dashes.py

# Trigger Worker. No network, no credentials needed.
cd infra/trigger-worker && npm test

# Frontend. Run BOTH: tsc catches config errors vite build passes over.
cd web && npm install && npm run build && npm test
```

CI runs all of the above on every push touching the relevant paths.

### Conventions worth knowing before your first commit

- **LF line endings everywhere**, enforced by `.gitattributes` from the first
  commit. A CRLF inside a workflow heredoc makes bash compare the terminator
  against `PY\r`, never find it, and fail opaquely on a runner you cannot
  inspect.
- **No en dashes or em dashes** in code, comments, docs, UI copy or commit
  messages. Use commas, colons or parentheses. CI enforces it.
- **Pinned runner and actions.** `ubuntu-24.04`, not `ubuntu-latest`, which began
  migrating to Ubuntu 26 on 2026-10-19. A scoring pipeline whose OS image moves
  underneath it is not reproducible.
- **Every threshold is a named constant** in `pipeline/detect/constants.py`,
  with a comment recording where the number came from.
- **Time windows key off data timestamps, never run times.** A run can start
  hours late or not at all, so "the last 15 minutes" must mean the last 15
  minutes of data.
- **Small, single purpose commits.** A change that bundles two things leaves two
  possible explanations for whatever happens next.
