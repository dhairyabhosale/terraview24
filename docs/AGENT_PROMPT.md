### Non negotiable ground rules

1. **The anomaly baseline is mandatory.** Without a multi year seasonal baseline this project is a feed renderer with a globe attached. If you find yourself about to place a pin from a raw detection, stop. Every pin is a clustered event scored against a historical norm, or is explicitly labelled as unscorable.

2. **Never claim more than the data supports.** A confirmed pin says "VIIRS detected sustained anomalous thermal activity, 4.2 sigma above the regional October norm, corroborated across three passes, matching coverage found." It does not say "forest destruction here." The `headline_claim` string is generated by the pipeline so the frontend cannot overstate it. This restraint is the project's credibility, and it applies to the page's claims about itself too.

3. **News never places a pin.** GDELT is a confirmation layer only. Media coverage volume measures media attention, not event frequency. That asymmetry is the mechanism behind the `UNREPORTED` stage, which is the project's original contribution.

4. **Zero budget, no application server, no database.** Scheduled GitHub Actions write static JSON to an orphan `data` branch. A static Vercel frontend fetches it at runtime. No secret ever reaches the client bundle. If the frontend needs a key, the design is wrong. The one disclosed exception is the trigger layer: a free Cloudflare Worker and one narrowly scoped token. State it in the README as "one credential and one always on component", never as "zero servers".

5. **Never render raw detections.** Cluster in the pipeline. Hard cap 3000 interactive features. `BillboardCollection`, never individual Cesium `Entity` objects. A globe that stutters discredits the analysis underneath it.

6. **Build the frontend against fixtures.** `DATA_CONTRACTS.md` is the only coupling between tiers, so frontend and pipeline proceed in parallel from day one. Do not wait for live data to start the globe. The fixtures must include the awkward cases that file lists.

7. **Depth over breadth.** Four well validated detectors beat twelve that fire noise. A reviewer will test the weakest pin.

8. **Never use an em dash or an en dash** in code comments, documentation, commit messages, UI copy or any other output. Use commas, colons or parentheses. Check for them before every commit.

9. **Do not drop any part of the project scope.** Every event type in `ARCHITECTURE.md` section 4 stays in scope until it is demonstrated that no viable route exists. Deferring something to a later phase is fine and expected; **deleting it is not.** If you conclude a feature is impossible, say so explicitly, state exactly what you tried, name the specific blocker, and ask before removing it.

   This rule governs *what gets built*, not *what gets built first*. Rule 7 still governs order.

10. **A dead API is a research task, not a blocker.** If a source is retired, rate limited beyond usefulness, or has moved behind paid or interactive auth, find the best free alternative and propose it with a comparison: what it gives you, what resolution and cadence, what you lose, and how the detection method changes. Common routes: Microsoft Planetary Computer, Copernicus Data Space, NASA Earthdata, Earth Engine, the AWS open data registry. **Report the alternative and wait for a decision.** Do not drop the capability, and do not switch sources silently.

11. **Measure platform behaviour, do not assume it.** Free platforms behave in ways documentation does not predict. Anything timing related gets a **time based** stopping rule, not a count of windows: GitHub's scheduler had a 4.7 hour median delay, so ninety quiet minutes proved nothing. Change one variable at a time, observe, then the next. Never push a change that destroys the condition an experiment is running under.

12. **Validate, do not just parse. Observe, do not just read back.** A YAML parser accepted a workflow that GitHub Actions rejected on every push. Run `actionlint`. After every fix, observe the effect the fix was meant to have (a build that no longer appears, a run that now succeeds) and record that observation. A setting read back from a dashboard is not evidence. Look at the Actions tab after the first push, not only after runs you started on purpose.

13. **Say what you did not verify.** End each report with what was verified versus what was assumed, for example "page served and configured, but JavaScript not executed in a browser". Recommend a check the human can do for the rest.

### Your first task: Phase 0 only

Do **not** start Phase 1. Phase 0 proves the architecture end to end, including the trigger, before any real work. It is in three parts, specified in full in `ROADMAP.md`.

**0a. Names and sources.** Step 0: confirm the name is free on GitHub and Vercel (actually assign the host in Vercel). Then re verify the keyless endpoints in `DATA_SOURCES.md` with live requests and report **only what differs**. If nothing differs, continue without waiting. **0b. Scaffold, data branch, page.** Scaffold the repo per `ARCHITECTURE.md` section 3. Build the orphan `data` branch with git plumbing and push it before any workflow first runs. Commit a `vercel.json` onto `data` itself so its writes do not trigger Vercel builds, and verify by observation that they do not. Write `heartbeat.yml`, the page, `actionlint` locally and in CI, the concurrency group, and the pinned runner and checkout versions. Ingest workflows ship inert behind their gates.

**0c. Trigger layer.** Build `infra/trigger-worker/` with its tests and a README for the human. Add `workflow_dispatch` with a `source` input to every workflow, keeping `schedule` as fallback. Measure dispatch to `created_at` lag three times. Build the page's honest state display and its staleness message.

**Before you start, give me one numbered checklist of every action only I can do**, in the order `ROADMAP.md` lists them, each with exact click paths or commands. Do not make me discover them one at a time.

**Phase 0 exits when a number changes on a deployed page because a job wrote it with no human involved.** A `schedule` or external timer write counts. A manual dispatch does not. Do not relax this to make it pass. If it cannot pass, that is a finding to report, with the measurements.

### How to work

- Report once after 0a only if something differs from the docs. Otherwise proceed.
- Flag any point where a spec document is ambiguous or where you disagree with an approach, rather than silently picking an interpretation. Flag errors in the specs too: the first attempt found a double log in the sigma formula, a stale section header and an undefined enum, and caught each before code depended on it.
- Where a specification gives a tuning value (DBSCAN `eps`, the time scaling constant, the baseline thresholds, `COVERAGE_MIN`, animation durations, the click angle threshold), treat it as a starting point to be tuned empirically, and record the value you settle on in the doc.
- Keep the doc set in `docs/` current as decisions are made. Specification drift between docs and code is what makes a project like this unmanageable three weeks in.
- Keep commits small and single purpose. A change that bundles two things leaves two possible explanations for whatever happens next.
- One change at a time when diagnosing anything.

## Notes for you, not the agent

**Before you send this:** nothing else needs deciding. The name check is the agent's step 0, but you can pre check it yourself: in Vercel, add `terraview24.vercel.app` to any project and see whether it is assigned. A deleted project's old host can take a little while to free up.

**If you want to cut the human steps:** the trigger layer is the part with the Cloudflare account and the token. You can tell the agent to skip it and accept GitHub's cadence of roughly one run per 4 to 5 hours. The page then states that cadence honestly. That removes the token, the Worker and about half of your checklist, at the cost of slower updates. `ARCHITECTURE.md` section 1a describes this fallback.

**Watch for three specific failure modes as the agent works:**

The first is jumping to Phase 3. The `UNREPORTED` layer is the most interesting part and the one an agent will want to build. It is meaningless without a validated baseline underneath.

The second is quietly weakening the baseline requirement because the Tier 0 notebook is tedious. If it proposes "a simpler threshold for now," that is the whole project being hollowed out.

The third is declaring a timing fault too early. If a scheduled run has not appeared, ask how long it has actually been, against the measured delays in `ARCHITECTURE.md` section 1a, before agreeing to any diagnosis.

**On rules 9 and 10.** These are deliberately worded to force a conversation rather than a silent decision. The failure they prevent is not an agent that gives up loudly; it is one that quietly substitutes a weaker source or trims a detector and reports success. Expect several "this source changed, here is the alternative" reports, and treat each as a real decision point. A substitution that loses resolution or cadence changes what the detector can honestly claim, which flows all the way through to the panel copy.

**On Family E.** Trimmed to two subtypes, both surface water boundary problems sharing one NDWI implementation. `land_subsidence` and `excavation_terrain_change` were assessed and cut with reasoning recorded in `ARCHITECTURE.md` section 4. That pair of cuts is the worked example of ground rule 9 done correctly: assessed against a specific blocker, reasoning written down, intent preserved where possible.

**What changed from the first attempt, in one list.** One name. A trigger layer built from measured scheduler behaviour. The `data` branch kept out of Vercel builds. `actionlint` in place of a YAML parse. The baseline moved to NOAA-20. Corroboration typed by independence. GDELT through bulk files. Frozen event ids. Honest baseline grading with an unscored path. A staleness message on the page. No "real time" until a latency is measured.
